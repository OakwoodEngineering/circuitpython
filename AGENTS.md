# Current MRAM implementation — 2026-09-12

The implemented target is **nyansat_obk_mram**, separate from nyansat_obk. The
prototype's OTP repair is programmed/enabled and autonomous cold boot passed.
Do not repeat provisioning or treat OTP as virgin. See the current
[board documentation](ports/raspberrypi/boards/nyansat_obk_mram/README.md).

CPU 150 MHz; MRAM EB/F0 1-4-4 SDR, 37.5 MHz, latency 12, RX2; PSRAM 75 MHz,
RX1, MAX_SELECT 6. OTP → SRAM repair provides zero-latency SPI for ROM before
CircuitPython selects quad XIP. The 2 MiB MRAM holds 1020 KiB firmware reservation,
4 KiB NVM and 1 MiB FAT. Firmware exclusion from filesystem writes is a software
bound, not enabled hardware MRAM protection. The MRAM-specific NVM path is enabled.

The sibling pico-sdk repo owns tools/mram_swd sources, system/memory architecture
documents, immutable review packages and qualification/programming captures.
This repository uses its own ports/raspberrypi/sdk submodule for builds. Preserve
unrelated submodule/untracked work when committing MRAM changes.

The initial plan below is historical and superseded where it differs from the
implemented board. In particular, its phase-1 disabled-NVM and original target
name are not current build instructions.

# RP2350 + ASxxxx204 MRAM Bring-Up Plan (nyansat_obk)

## Goal
Add reliable MRAM XIP boot and CIRCUITPY filesystem support for `ports/raspberrypi/boards/nyansat_obk`, using `boot2_asxxxx204.S` and a protected MRAM memory map.

## Feasibility Summary
- Feasible: **Yes**, with medium integration risk.
- Biggest deltas from the initial plan:
  - CircuitPython in this tree uses a FAT block device path (`supervisor/shared/flash.c` + `oofatfs`), not LittleFS.
  - RP2350 boot2 for this port is generated by `ports/raspberrypi/gen_stage2.py` in the Make build, not selected via Pico SDK board CMake by default.
  - `common-hal/nvm/ByteArray.c` currently assumes flash erase/program APIs; this must be adapted or disabled for MRAM-first bring-up.

## Revised Implementation Plan

### 0) Preconditions and decisions
- Assume MRAM density for first target is **16 Mbit (2 MiB)**.
- Phase 1 sets `CIRCUITPY_INTERNAL_NVM_SIZE` to `0` to avoid unsafe flash-only NVM writes.
- Keep `INTERNAL_FLASH_FILESYSTEM = 1`; replace the raspberrypi internal flash backend implementation with MRAM-aware operations for this board.

Acceptance criteria:
- Build configuration is explicit about MRAM size and backend selection.

### 1) Integrate ASxxxx204 boot2 into the CircuitPython build path
Task:
- Move `boot2_asxxxx204.S` to `ports/raspberrypi/boot_stage2/boot2_asxxxx204.S`.
- Add a Makefile-selectable boot2 source for RP2350 (board override), instead of always compiling generated `stage2.c`.
- Set board flags in `ports/raspberrypi/boards/nyansat_obk/mpconfigboard.mk` to pick this boot2.

Notes:
- The current path (`gen_stage2.py` + `boot_stage2/RP2350.c.jinja`) must remain default for other boards.
- Keep compile defs for latency/clock divider board-tunable (`PICO_MRAM_XIP_READ_LATENCY`, `PICO_FLASH_SPI_CLKDIV`, `PICO_FLASH_SPI_RXDELAY`).

Acceptance criteria:
- `nyansat_obk` links with `boot2_asxxxx204`.
- Boot2 image satisfies stage2 size constraints and enters XIP successfully.

### 2) Define and enforce MRAM memory map
Task:
- Use explicit protected/app/FS ranges.

Initial map for 2 MiB MRAM:
- Protected firmware/XIP region: `[0x000000, 0x100000)` (1 MiB)
- Filesystem region: `[0x100000, 0x200000)` (1 MiB)
- NVM region: none in Phase 1 (`CIRCUITPY_INTERNAL_NVM_SIZE = 0`)

Notes:
- FS start and size are 4 KiB aligned.
- Protected range is immutable to filesystem writes.

Acceptance criteria:
- Any write/erase targeting `< FS_START` is rejected.

### 3) Implement MRAM storage backend for raspberrypi supervisor
Task:
- Add an MRAM backend used by `ports/raspberrypi/supervisor/internal_flash.c` when `USE_MRAM_STORAGE=1`.
- Required primitives:
  - `read(addr,len)`
  - `write(addr,len,data)`
  - `erase(block)` as `write(0xFF...)` for erase-less MRAM
  - `sync()`

Command path:
- Implement and verify: `0x06` (WREN), `0x05` (RDSR), write command (`0x02` or device-specific fast write), read command (`0x03` first; optional `0x0B/0xBB/0xEB` later).

Notes:
- Do not call `flash_range_erase/program` or ROM flash helpers in MRAM mode.
- Keep filesystem block cache behavior (sector-sized cache) unless profiling shows it is unnecessary.

Acceptance criteria:
- FAT read/write/format succeeds through MRAM backend only.

### 4) Wire board configuration to select MRAM storage
Task:
- In `nyansat_obk` board config, set compile-time switch (`USE_MRAM_STORAGE=1`) and MRAM total size.
- Ensure block count is computed from MRAM size, not flash RDID assumptions.

Notes:
- Existing `internal_flash.c` currently reads RDID using flash helper path; this should be bypassed in MRAM mode.

Acceptance criteria:
- `supervisor_flash_get_block_count()` matches configured MRAM filesystem size.

### 5) XIP-safe write path
Task:
- Place MRAM transaction functions in SRAM (`__no_inline_not_in_flash_func` / equivalent attributes).
- Keep critical sections minimal around direct QMI transactions.

Notes:
- Current flash pre/post write disables interrupts; verify if additional multicore lockout is needed on RP2350.

Acceptance criteria:
- No hard faults or lockups during sustained filesystem writes while executing from XIP.

### 6) Validation gates
1. Build gate:
- `make -C ports/raspberrypi BOARD=nyansat_obk` passes.

2. Boot gate:
- Board boots to CircuitPython REPL with MRAM boot2.

3. Filesystem gate:
- First-boot format succeeds.
- `code.py` create/edit/delete cycles succeed over USB MSC.

4. Protection gate:
- Deliberate write attempts below `FS_START` fail cleanly.

5. Stability gate:
- Reboot and power-cycle retention checks pass.
- Repeated write stress test does not corrupt firmware region.

## Risks and mitigations
- Risk: boot2 size/entry incompatibility.
  - Mitigation: add explicit build check for padded stage2 and symbol placement; fail build early.

- Risk: wrong MRAM command variant (write/read opcode and latency coupling).
  - Mitigation: keep command macros centralized and board-tunable; begin with conservative single-lane read/write before optimizing.

- Risk: NVM path corrupts protected region.
  - Mitigation: disable NVM in Phase 1; reintroduce with shared MRAM protected-write API.

- Risk: small capacity SKUs (1/4/8 Mbit) are insufficient for CircuitPython firmware + FS.
  - Mitigation: support only 16 Mbit for initial target; enforce compile-time size checks.

## Out of scope for Phase 1
- LittleFS migration.
- Multi-density auto-detection with dynamic partitioning.
- Performance optimization beyond baseline reliable operation.
